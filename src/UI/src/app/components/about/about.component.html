About this application

Customer Management System is a full-stack demo application built to showcase a realistic, end-to-end CRUD workflow: an Angular single-page frontend talking to an ASP.NET Core Web API, which persists data in SQL Server through raw ADO.NET calls to stored procedures — no ORM in between. A merchant signs in and manages customers, the product catalogue and customer purchases.

Running it locally

The database is a containerized SQL Server (Azure SQL Edge, which also runs natively on Apple Silicon). Started by hand, that's: 

docker pull mcr.microsoft.com/azure-sql-edge

docker run -e "ACCEPT_EULA=1" -e "MSSQL_SA_PASSWORD=MyStrongPassw0rd?" -p 1433:1433 --name sqlserver --platform linux/arm64 -d mcr.microsoft.com/azure-sql-edge

On macOS and Linux the API always uses that container. On Windows it uses the container if it answers within 3 seconds, and otherwise falls back to a locally installed SQL Server (Windows authentication); the choice is logged at startup.

Once the container is up and the schema is deployed (see Database below), the two remaining pieces both need to be started:

  • API — the ASP.NET Core Web API project at https://localhost:7145, run with dotnet run (or from your IDE). It serves the REST endpoints and talks to SQL Server over ADO.NET.
  • Angular frontend — the SPA at http://localhost:4204, run with ng serve / npm start. It calls the API over HTTPS for authentication and every customer and product operation.

Both must be running at the same time — the UI has no data or logic of its own beyond forms and validation; everything it shows comes live from the API. If the API isn't reachable, the UI notices within a few seconds (it polls a lightweight /health endpoint) and shows a plain "API is not running" message in place of the page, instead of failing silently or showing stale data.

Build & run scripts

Two scripts at the repository root wrap all of the above so nothing needs to be pieced together by hand:

  • ./build.sh — a CI-style, one-shot build: restores and builds the .NET solution, runs its test suite, builds the SQL database project, then installs, format-checks, builds and tests the Angular app. It doesn't start anything; it just proves everything compiles and the tests pass.
  • ./run.sh — the actual local dev environment. It makes sure Docker is running (starting Docker Desktop on macOS if needed), starts the Azure SQL Edge container if it isn't already up (pulling and creating it on first run), builds the database project and publishes its schema straight into that container, then launches the API in the background and the Angular dev server in the foreground. Ctrl+C stops both.

run.sh is safe to re-run any time: an existing, already-initialized database is simply left alone (schema deploys are a diff, not a wipe-and-recreate — so any customers you've registered through the UI survive a re-run), and a stopped container is restarted rather than recreated.

Database

The schema lives in its own SQL Server Database Project (a .sqlproj), not in migration scripts run by the API. run.sh builds that project into a .dacpac and deploys it with sqlpackage, retrying automatically until the freshly-started container starts accepting connections. On a fresh server that one publish creates the database and everything in it. This deploy is a diff against the container's current state, so it's idempotent — running it again against an already-initialized database changes nothing — and it's allowed to rebuild already-populated tables when a schema change requires it (e.g. adding a constraint), since this is disposable local dev data, not a production database that needs that guardrail.

The schema has six tables:

  • Customer — one row per customer: name, email, phone number, gender, birth date, a numeric StatusCode (active / deactivated / test), an enrollment date (when they first became a customer, which can predate this system), and creation/last-interaction timestamps, keyed by a CustomerId (GUID) primary key. Email and phone number each carry a unique constraint, so duplicates are rejected by the database itself, not just application logic.
  • CustomerAddress — one row per customer's address, linked back to Customer by a foreign key on that same CustomerId.
  • Merchant — login accounts for the API, keyed by Username (primary key): a PBKDF2 password hash and its salt (never the plaintext password), a role, and the time of the last successful login.
  • Product — the catalogue: name, category, description, price, the depot it's stored in, and both its initial quantity and the quantity still on hand (so "sold" is the difference).
  • CustomerPurchase — one row per purchase, linking a customer to a product with the time it was bought.
  • CustomerAuditLog — one row per change to a customer (created, edited, deactivated, reactivated, deleted, purchased). It deliberately has no foreign key to Customer, so a customer's history survives its deletion.

All reads and writes go through stored procedures, named <Entity>_<Verb>, rather than ad-hoc SQL from the API:

  • Customer_Create — inserts the customer and address rows in one transaction, rejecting duplicate email/phone number first.
  • Customer_Get — looks up a single customer by ID, phone number, or email.
  • Customer_List — returns one page of customers joined with their addresses, filtered by an optional search term (name, email, or phone number) and sorted by name/email/phone number, plus a total count for pagination.
  • Customer_Update — updates only the fields that were actually supplied, leaving the rest untouched.
  • Customer_Deactivate / Customer_Reactivate — deactivating remembers the status the customer had, and reactivating restores it (so a test customer comes back as a test customer); both refuse to "change" a customer to the state it's already in.
  • Customer_Delete — hard-deletes a customer with its purchases and address, but only once it's deactivated (or is a test customer).
  • CustomerPurchase_Create / CustomerPurchase_ListByCustomer — record and list purchases. Recording one checks that the customer exists and isn't deactivated and that the product is in stock, then decrements the stock and inserts the purchase in one transaction.
  • Product_List / Product_GetDetails / Product_Create — the catalogue, one product with its buyers, and adding a product.
  • CustomerAuditLog_Create / CustomerAuditLog_ListByCustomer / CustomerAuditLog_List / CustomerAuditLog_DeleteAll — write, read (one customer's trail, or the global one, paged) and clear the audit log.
  • Report_GetCustomerInsights — feeds the charts page: one anonymous row per customer (no names or contact details) plus purchases and revenue per month.
  • Merchant_GetAuthData / Merchant_RecordLogin — return a merchant's password hash, salt, and role for the login flow, and stamp the time of a successful login.

A post-deployment script seeds one demo login (it's skipped if that merchant already exists), so there's something to sign in with immediately after initialization: username TestMerchantID, password Merchant123. It also seeds a catalogue of 50 products, inserting only the ones that are missing, so a redeploy never resets their stock.

Security flow

Authentication is stateless, bearer-token based — there are no server-side sessions and no auth cookies:

  1. The login form submits a username and password to POST /api/authentication/access-token over HTTPS. That endpoint is rate-limited (5 attempts per minute per caller IP) — beyond that it responds with 429 immediately, without touching the database, to blunt scripted brute-force/credential-stuffing attempts.
  2. The API fetches only that merchant's stored password hash and salt via a stored procedure (dbo.Merchant_GetAuthData), executed through a parameterized ADO.NET SqlCommand — the username is always bound as a command parameter, never concatenated into SQL, so this path is not vulnerable to SQL injection.
  3. The submitted password is re-hashed with PBKDF2-SHA256 (100,000 iterations, per-user salt) and compared to the stored hash using a constant-time comparison — the plaintext password is never stored anywhere. An unknown username is hashed against a dummy salt, so it takes as long as a wrong password and doesn't reveal which usernames exist.
  4. On success, the API mints a JWT signed with HMAC-SHA256 (the same signing-key logic is shared by issuing and validating, so they can never quietly drift apart). It carries the username (as several standard claim types), the merchant's role, a marker for how they authenticated, a unique token ID, and issued time, with a configured expiry.
  5. The Angular app stores that token in sessionStorage (cleared automatically when the tab closes) and attaches it as an Authorization: Bearer header on every subsequent call to the API — and only to the API, never to any other host.
  6. Every protected endpoint is decorated with [Authorize]; ASP.NET's JWT bearer middleware verifies the signature, issuer, audience, and expiry on each request — independent of anything the browser claims. Clearing the global audit log additionally requires the merchant role.
  7. On navigation, an Angular route guard double-checks the token against a dedicated verify-token endpoint; if a token is missing, expired, or rejected (or any API call comes back with 401), the app clears the stored token and redirects to the login page.

Because the token travels in a header rather than a cookie, the app is not exposed to CSRF; the main residual risk of this pattern is XSS (any injected script could read the token from sessionStorage), which is why the frontend avoids unsanitized HTML rendering.

Data access & errors

All data access goes through ADO.NET SqlCommand objects calling the stored procedures listed under Database above, with every input passed as a typed, bound parameter — nothing is built by string-concatenating SQL. That gives the API the standard CRUD set (create, read one or all, update) plus the deactivate/reactivate/delete lifecycle, purchases, products, the audit log and the charts data, all exposed through the [Authorize]-protected CustomerController and ProductController endpoints the Angular app calls.

Every write procedure reports its outcome as a result row: success, or the HTTP status that fits (400 for a bad reference, 404 for not found, 409 for a duplicate or a state conflict). Every error the API returns is an RFC 9457 Problem Details response, which the UI reads to show a specific message next to the control that failed; anything unexpected is logged once and returned as a 500.

Console-logged API calls

Since this is a showcase app, every HTTP call the Angular frontend makes to the API is mirrored to the browser's devtools console via apiLoggerInterceptor, a functional HttpInterceptorFn registered in app.config.ts. Open devtools (F12 or Cmd/Ctrl+Shift+I) and watch the Console tab while using the app:

  • A blue → METHOD url line is logged when a request goes out, with its request body attached.
  • A green ← METHOD url status (Nms) line is logged when the response comes back successfully, with the response body and how long it took.
  • A red ✖ METHOD url status (Nms) line is logged instead if the request fails.

Login/password fields are redacted before logging (shown as ••••••••), and nothing is logged during server-side rendering — only in the browser.

Generate test customers

This is test data. The button below registers 50 fictitious customers through the same POST /api/customer/create endpoint the Add customer form uses — each with a randomly generated name, email, a Romanian mobile number (07xxxxxxxx), a home address, and an enrollment date between 2005 and 2025. Every one of them is created with the Test status (1904) rather than Active, so they're clearly distinguishable from real customers everywhere the status is shown. It exists purely so there's enough data to try out search, sorting, pagination, and the charts locally; like an active customer, a test customer can still be deactivated, and it can be deleted straight away.

Each test customer also buys between 1 and 5 different products from the catalogue, picked at random from what's still in stock (through POST /api/customer/purchase, the same endpoint as the Record purchase control on a customer's page). Those purchases are real: they use up product stock, and deleting a test customer later does not put the stock back — so generating test customers repeatedly will eventually sell products out.

What you can do in the UI

  • Log in with merchant credentials to start a session, and log out explicitly from the top nav when you're done.
  • Browse the customer table, paged and sorted by the API itself: search (by name, email, or phone), column sorting, and Previous/Next all re-query the server for just the requested page rather than filtering an already-loaded list.
  • Add a new customer through a validated form (name, contact details, address, birth and enrollment dates via a native date picker, etc.); leaving a form with unsaved changes asks first.
  • Open a customer's details page for a full read-only view, with a plain-language account status instead of a raw code, their purchases, and their audit trail.
  • Edit an existing customer's information.
  • Record a purchase for a customer from their details page, which takes one unit out of that product's stock.
  • Deactivate an active customer (with a confirmation prompt), or reactivate one that was deactivated.
  • Permanently delete a customer once it has been deactivated, or a test customer at any time (also confirmation-guarded).
  • Select several customers at once with row checkboxes and run a bulk action: active customers in the selection are deactivated, already-deactivated (or test) customers are permanently deleted — a confirmation prompt spells out how many of each before anything happens.
  • Export the currently filtered/sorted customer list to a CSV file.
  • Browse the product catalogue (sortable by name, category, depot, price, and sold / inventory / left), add a product, and open one to see its stock and who bought it.
  • Explore the charts dashboard: key figures at a glance, the customer base (enrollments, growth, status, gender, age, loyalty, counties, purchases per customer), and sales and catalogue (revenue over time, categories, stock health).
  • Browse a global, paginated audit trail of every customer change (create/edit/deactivate/reactivate/delete/purchase) across the whole system, newest first, and clear it.
  • Get redirected to login automatically if your session expires or is rejected by the API.
