About this application

Customer Management System is a full-stack demo application built to showcase a realistic, end-to-end CRUD workflow: an Angular single-page frontend talking to an ASP.NET Core Web API, which persists data in SQL Server through raw ADO.NET calls to stored procedures — no ORM in between.

Running it locally

The database is a containerized SQL Server (Azure SQL Edge, which also runs natively on Apple Silicon). Started by hand, that's: 

docker pull mcr.microsoft.com/azure-sql-edge

docker run -e "ACCEPT_EULA=1" -e "MSSQL_SA_PASSWORD=MyStrongPassw0rd?" -p 1433:1433 --name sqlserver --platform linux/arm64 -d mcr.microsoft.com/azure-sql-edge

Once the container is up and the schema is deployed (see Database below), the two remaining pieces both need to be started:

  • API — the ASP.NET Core Web API project, run with dotnet run (or from your IDE). It serves the REST endpoints and talks to SQL Server over ADO.NET.
  • Angular frontend — the SPA, run with ng serve / npm start. It calls the API over HTTPS for authentication and every customer operation.

Both must be running at the same time — the UI has no data or logic of its own beyond forms and validation; everything it shows comes live from the API. If the API isn't reachable, the UI notices within a few seconds (it polls a lightweight /health endpoint) and shows a plain "API is not running" message in place of the page, instead of failing silently or showing stale data.

Build & run scripts

Two scripts at the repository root wrap all of the above so nothing needs to be pieced together by hand:

  • ./build.sh — a CI-style, one-shot build: restores and builds the .NET solution, runs its test suite, builds the SQL database project, then installs and builds the Angular app. It doesn't start anything; it just proves everything compiles and the tests pass.
  • ./run.sh — the actual local dev environment. It makes sure Docker is running (starting Docker Desktop on macOS if needed), starts the Azure SQL Edge container if it isn't already up (pulling and creating it on first run), builds the database project and publishes its schema straight into that container, then launches the API in the background and the Angular dev server in the foreground. Ctrl+C stops both.

run.sh is safe to re-run any time: an existing, already-initialized database is simply left alone (schema deploys are a diff, not a wipe-and-recreate — so any customers you've registered through the UI survive a re-run), and a stopped container is restarted rather than recreated.

Database

The schema lives in its own SQL Server Database Project (a .sqlproj), not in migration scripts run by the API. run.sh builds that project into a .dacpac and deploys it with sqlpackage, retrying automatically until the freshly-started container starts accepting connections. This deploy is a diff against the container's current state, so it's idempotent — running it again against an already-initialized database changes nothing — and it's allowed to rebuild already-populated tables when a schema change requires it (e.g. adding a constraint), since this is disposable local dev data, not a production database that needs that guardrail.

The schema has three tables:

  • Customer — one row per customer: name, email, phone number, gender, birth date, a numeric StatusCode (active / deactivated), and creation/last-interaction timestamps, keyed by a CustomerId (GUID) primary key. Email and phone number each carry a unique constraint, so duplicates are rejected by the database itself, not just application logic.
  • CustomerAddress — one row per customer's address, linked back to Customer by a foreign key on that same CustomerId.
  • Merchant — login accounts for the API, keyed by Username (primary key): a PBKDF2 password hash and its salt (never the plaintext password), a role, and a last-interaction timestamp.

All customer/merchant reads and writes go through stored procedures rather than ad-hoc SQL from the API:

  • Customer_Create — inserts the customer and address rows in one transaction, rejecting duplicate email/phone number first.
  • Customer_Get — looks up a single customer by ID, phone number, or email.
  • Customer_List — returns one page of customers joined with their addresses, filtered by an optional search term and sorted by name/email/phone number, plus a total count for pagination.
  • Customer_Update — updates only the fields that were actually supplied, leaving the rest untouched.
  • Customer_Deactivate / Customer_Reactivate — flip StatusCode, refusing to "change" it to the state it's already in.
  • Customer_Delete — hard-deletes a customer and its address, but only once it's already deactivated.
  • Merchant_GetAuthData — returns a merchant's password hash, salt, and role for the login flow, and stamps their last-interaction time.

A post-deployment script seeds one demo login the first time the schema is deployed (it's skipped if that merchant already exists), so there's something to sign in with immediately after initialization: username TestMerchantID, password Merchant123.

Security flow

Authentication is stateless, bearer-token based — there are no server-side sessions and no auth cookies:

  1. The login form submits a username and password to POST /api/authentication/access-token over HTTPS. That endpoint is rate-limited (5 attempts per minute per caller IP) — beyond that it responds with 429 immediately, without touching the database, to blunt scripted brute-force/credential-stuffing attempts.
  2. The API fetches only that merchant's stored password hash and salt via a stored procedure (dbo.Merchant_GetAuthData), executed through a parameterized ADO.NET SqlCommand — the username is always bound as a command parameter, never concatenated into SQL, so this path is not vulnerable to SQL injection.
  3. The submitted password is re-hashed with PBKDF2-SHA256 (100,000 iterations, per-user salt) and compared to the stored hash using a constant-time comparison — the plaintext password is never stored anywhere.
  4. On success, the API mints a JWT signed with HMAC-SHA256 (the same signing-key logic is shared by issuing and validating, so they can never quietly drift apart). It carries the username (as several standard claim types), the merchant's role, a marker for how they authenticated, a unique token ID, and issued time, with a configured expiry.
  5. The Angular app stores that token in sessionStorage (cleared automatically when the tab closes) and attaches it as an Authorization: Bearer header on every subsequent API call.
  6. Every protected endpoint is decorated with [Authorize]; ASP.NET's JWT bearer middleware verifies the signature, issuer, audience, and expiry on each request — independent of anything the browser claims.
  7. On navigation, an Angular route guard double-checks the token against a dedicated verify-token endpoint; if a token is missing, expired, or rejected (or any API call comes back with 401), the app clears the stored token and redirects to the login page.

Because the token travels in a header rather than a cookie, the app is not exposed to CSRF; the main residual risk of this pattern is XSS (any injected script could read the token from sessionStorage), which is why the frontend avoids unsanitized HTML rendering.

Data access & CRUD operations

All customer data access goes through ADO.NET SqlCommand objects calling the stored procedures listed under Database above, with every input passed as a bound parameter — nothing is built by string-concatenating SQL. That gives the API the standard CRUD set (create, read one or all, update) plus the deactivate/reactivate/delete lifecycle described below, all exposed through the [Authorize]-protected CustomerController endpoints the Angular app calls.

Console-logged API calls

Since this is a showcase app, every HTTP call the Angular frontend makes to the API is mirrored to the browser's devtools console via apiLoggerInterceptor, a functional HttpInterceptorFn registered in app.config.ts. Open devtools (F12 or Cmd/Ctrl+Shift+I) and watch the Console tab while using the app:

  • A blue → METHOD url line is logged when a request goes out, with its request body attached.
  • A green ← METHOD url status (Nms) line is logged when the response comes back successfully, with the response body and how long it took.
  • A red ✖ METHOD url status (Nms) line is logged instead if the request fails.

Login/password fields are redacted before logging (shown as ••••••••), and nothing is logged during server-side rendering — only in the browser.

Generate test customers

This is test data. The button below registers 50 fictitious customers through the same POST /api/customer/create endpoint the Register customer form uses — each with a randomly generated name, email, a Romanian mobile number (07xxxxxxxx), and a home address. Every one of them is created with the Test status (1904) rather than Active, so they're clearly distinguishable from real customers everywhere the status is shown. It exists purely so there's enough data to try out search, sorting, and pagination locally; like an active customer, a test customer can still be deactivated and deleted afterwards.

Each test customer also buys between 1 and 5 different products from the catalogue, picked at random from what's still in stock (through POST /api/customer/purchase, the same endpoint as the Record purchase control on a customer's page). Those purchases are real: they use up product stock, and deleting a test customer later does not put the stock back — so generating test customers repeatedly will eventually sell products out.

What you can do in the UI

  • Log in with merchant credentials to start a session, and log out explicitly from the top nav when you're done.
  • Browse the customer table, paged and sorted by the API itself: search (by name, email, or phone), column sorting, and Previous/Next all re-query the server for just the requested page rather than filtering an already-loaded list.
  • Register a new customer through a validated form (name, contact details, address, birth date via a native date picker, etc.).
  • Open a customer's details page for a full read-only view, with a plain-language account status instead of a raw code.
  • Edit an existing customer's information.
  • Deactivate an active customer (with a confirmation prompt), or reactivate one that was deactivated.
  • Permanently delete a customer once it has been deactivated (also confirmation-guarded).
  • Select several customers at once with row checkboxes and run a bulk action: active customers in the selection are deactivated, already-deactivated (or test) customers are permanently deleted — a confirmation prompt spells out how many of each before anything happens.
  • Export the currently filtered/sorted customer list to a CSV file.
  • Browse a global, paginated audit trail of every customer change (create/edit/deactivate/reactivate/delete) across the whole system, newest first.
  • Get redirected to login automatically if your session expires or is rejected by the API.
