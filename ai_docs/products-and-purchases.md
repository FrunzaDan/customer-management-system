# Products & Purchases

## What it is

A seeded 50-product tech catalogue (`Product`, now extensible via an "Add product" form), a customer↔product purchase link table (`CustomerPurchase`), a "Purchases" card on customer details, and a **Products** tab (list + per-product detail showing who bought it and when).

## How it works

**Schema.** `Product`: `ProductId` (`UNIQUEIDENTIFIER`, `DEFAULT NEWSEQUENTIALID()`), `Name`, `Category`, `Description` (the API's `comment`), `Price` (`DECIMAL(10,2)`), `InitialQuantity` (units originally stocked, never changes; the API's `inventoryQuantity`), `QuantityOnHand` (units left; the API's `stockQuantity`), `Warehouse` (the API's `depot` — "depos" in the original request was read as *depot*), with `CHECK`s that Price ≥ 0 and `0 ≤ QuantityOnHand ≤ InitialQuantity`. `CustomerPurchase`: `CustomerPurchaseId` (identity — a customer can buy the same product repeatedly, so (customer, product) isn't a key), `CustomerId`, `ProductId` (both `UNIQUEIDENTIFIER`, named FKs), `PurchasedAt` (`DATETIME2(0)`, UTC, `DEFAULT SYSUTCDATETIME()`). Naming follows the project-wide convention in [database](database.md).

**Seed.** 50 products (17 categories) with **hard-coded GUIDs** (string literals `CONVERT`ed to `UNIQUEIDENTIFIER`), inserted by `INSERT … SELECT … WHERE NOT EXISTS (same GUID)` — so redeploying never duplicates products and never resets `QuantityOnHand` once purchases have decremented it. Fictional brand names on purpose (no factual claims about real products). An SSDT project allows **one** post-deploy script, so `PostDeployment.sql` `:r`-includes the merchants seed and the products seed; the two included files are `<None>` + `<Build Remove>` in the `.sqlproj` so they aren't also compiled as schema objects. **Adding a new NOT NULL column to an already-deployed `Product` needs a default** (or a drop/redeploy of the local dev DB) — the table has seeded rows.

**Sold / inventory / left.** `SoldQuantity` is **derived in SQL as `InitialQuantity - QuantityOnHand`**, not `COUNT(*)` of purchase rows. Reason: deleting a customer deletes their purchase rows but does *not* restore stock, so a count would shrink while "left" doesn't, and the three numbers stopped adding up. Consequence: the product-details buyers list only holds customers that still exist and can have fewer rows than `soldQuantity`; the page says so ("N sales were made to customers that have since been deleted").

**Recording a purchase** (`POST /api/Customer/purchase?customerGuid=&productGuid=`, `CustomerPurchase_Create`). Checks in order: customer exists (`404`), customer not deactivated `1903` (`409` — active *and* test customers may buy), product exists (`404`), stock > 0 (`409 Product is out of stock.`). Then, in **one transaction**, `UPDATE … SET QuantityOnHand = QuantityOnHand - 1 WHERE … AND QuantityOnHand > 0` (the guard lives in the `UPDATE` itself, not a read-then-write, so two buyers of the last unit can't both succeed) plus the `INSERT` of the purchase row. Quantity is always 1 per purchase. `CustomerPurchasing` validates both GUIDs (`400`), and on success writes a `Purchased` audit entry with details `Product: <name>` (best-effort, like every other mutation — see [database](database.md)). The proc's result row carries an extra `ProductName` column (only meaningful on `Result = 0`); `HandleResponseWithPurchaseResult` returns it as `Data`, `CustomerPurchasing` uses it for the audit entry and then **strips it** so the response keeps the "mutations carry no Data" convention.

**Deleting a customer** deletes their `CustomerPurchase` rows first, inside `Customer_Delete`'s existing transaction (the FK would otherwise block the delete). Unlike the audit log — which deliberately has no FK and outlives the customer — purchases are the customer's own data. Stock is **not** restored.

**Endpoints** (all on `CustomerController`, JWT-required): `GET /products` (all 50 — now 50+, since products can be added — category/name order, unpaginated), `GET /productDetails?productGuid=` (product + buyers, newest first; `Product_GetDetails` returns **two result sets** — product, then buyers — read with `NextResultAsync`; zero rows in the first = `404`), `GET /purchases?customerGuid=` (a customer's history, newest first, joined to product name/category/price), `POST /purchase`, `POST /product` (add a new product — see below). They sit on `CustomerController`/`ICustomerService`/`CustomerGetting` rather than a new controller, matching how the global audit log is already hosted there.

**Adding a product** (`POST /api/Customer/product`, `Product_Create`, `ProductRegistration.RegisterProductFunction`). Follows the same shape as customer registration: the request body is a `CreateProductRequest` (name, category, comment, price, inventoryQuantity, depot — it has no `guid`/`stockQuantity`/`soldQuantity` members at all; those are generated/computed server-side), `ProductRegistration` validates before ever calling the DB (name/category/depot required and length-capped via new `FieldLengthConstants.Product*` constants mirroring `Product`'s `NVARCHAR` lengths; comment length-capped if present; `Price` and `InventoryQuantity` must be **strictly positive** — a business rule, stricter than the DB's own `CHECK (Price >= 0)` — and `Price` must fit `DECIMAL(10, 2)`: at most two decimals, below 100,000,000). The new product's GUID is generated by the DB and returned as the response's `Data`, exactly like a customer's. `Product_Create` inserts the row with `QuantityOnHand = InitialQuantity` — a newly added product starts fully stocked, same as every seeded row. No duplicate-name check: `Product.Name` has no uniqueness constraint, so two products can share a name (the GUID is what's unique). **Not audit-logged**: `CustomerAuditLog.CustomerId` is `NOT NULL` with no generic/nullable variant, so `ICustomerAuditLogger` (built for customer-scoped actions) doesn't fit a product-only mutation; adding a product is the one mutating action in this app with no audit trail. Still no edit/delete for products (see Gotchas).

**UI.**
- *Customer details* → "Purchases" card: a `<select>` of products grouped by category (`<optgroup>`; each option shows price and stock, out-of-stock options disabled), a hint with the product's description/stock/depot, a "Record purchase" button, then a **Total spent** bar (`totalSpent`, a `computed` summing the listed purchases' prices in whole cents — client-side, no API field; it uses each product's *current* price, see Gotchas) and the history (product name links to its product page). After a successful purchase it re-fetches purchases, products (stock) and the audit trail; a failure (e.g. someone else took the last unit) shows an inline `role="alert"` and re-fetches stock. Disabled with an explanation for a deactivated customer (mirrors the proc's rule).
- *Products tab* (`/products`, nav link between Customers and Audit Log): an "Add product" button (top-right of the page header, mirroring the customer list's "Register customer" button) links to `/addProduct`; columns Product, Category, Depot, Price, **Sold**, **Inventory**, **Left** ("Sold out" badge at 0). Product name links to `/productDetails?id=<guid>`. Every column header is a sort `<button>` inside `<th aria-sort>` (same pattern and the shared `.sort-button` style from `styles.css` as the customer list). Sorting is **client-side** (`sortedProducts` computed) because the whole catalogue is already loaded — unlike the customer list, which sorts in SQL because it's paged. No sort until a header is clicked (rows keep the API's category/name order); first click ascending, second descending, a new column starts ascending; ties keep the API order (stable sort).
- *Add product* (`/addProduct`, `AddProductComponent`): mirrors `AddCustomerComponent` — Angular signal-forms (`@angular/forms/signals`), a `ProductFormModel` (all fields as strings, converted in `toProduct`), an `unsavedChangesGuard`-gated route plus a `beforeunload` listener for tab close/refresh, and the same invalid-summary/focus-first-error submission pattern. `product-form.ts` holds the schema (`required` on name/category/price/inventoryQuantity/depot; `pattern` on price — positive, ≤2 decimals — and inventoryQuantity — positive whole number) and `toProduct` (blank comment → `null`, price/inventoryQuantity → `Number(...)`). `ProductFormFieldsComponent` renders the fields, same role as `CustomerFormFieldsComponent` (not shared with it — different model shape — but not shared with an edit-product form either, since none exists yet). On success: `AddProductService.addProduct` posts to `POST /api/Customer/product`, shows a `'Product added successfully.'` toast, and the component navigates to `/products`.
- *Product details*: Stock card (Sold / Inventory / Left), Product card, and a Purchases table (customer — linked to their details page — email, when). One page header/`<h1>` is kept across loading, error and loaded states so the app's focus-the-`<h1>` navigation behaviour doesn't lose its target.
- `ProductService` (`httpResource`, lazily enabled by `loadProducts()`, `reload()`s on repeat calls since stock changes) feeds both the picker and the Products table; `ProductDetailsService`/`PurchaseService` follow `AuditLogService`'s guid-keyed `httpResource` pattern.

**Test customers get purchases too.** The About page's "Add 50 test customers" button (see [angular-frontend](angular-frontend.md)) gives **every** generated customer **1–5 different products**. It is a client-side loop over existing endpoints — no bulk endpoint — like the bulk delete: (1) fetch the catalogue once *before creating anything* (`ProductService.fetchProducts()`; if that fails, abort with an error toast rather than create 50 customers that were meant to have purchases); (2) for each customer, `POST /register` (silent variant) and take the new customer's GUID from the response's `data` (it used to be looked up again by email, one extra `GET` per customer, before registration returned it); (3) `chooseProductsToBuy` draws a count in 1–5 and that many **distinct, in-stock** products; (4) buy each with `PurchaseService.purchaseProductSilently` (no per-purchase toast — the summary is the only notification). A local copy of the catalogue is decremented as the run buys, so a product that hit 0 is no longer offered; a rejected purchase (e.g. `409` out of stock) zeroes that product locally, and a customer whose picks were *all* rejected is re-drawn up to 3 times. Everything runs sequentially. The final toast is `Added N test customers with P purchases.`; if some customers couldn't buy anything because the catalogue ran dry it becomes an **error** toast (`… (K could not buy anything — products are out of stock).`) — those customers still exist, they just have no purchases. **These purchases are real**: they consume stock, write `Purchased` audit rows, and deleting a test customer later does not restore stock (see above), so repeated generation eventually sells the catalogue out (~150 units per click against ~2,550 seeded).

## Gotchas / conventions

- `Price` on a purchase row is the product's **current** price, not what was paid — there's no price snapshot. Fine while the catalogue is fixed and there's no price-edit UI; add a `PricePaid` column if that ever changes.
- Products can now be **added** (`POST /api/Customer/product`, `/addProduct`) — the "seed-only, no add/edit/delete" rule from the original design was deliberately relaxed for this one operation. **Editing and deleting products are still unsupported** — no UI, no endpoint, no stored proc for either. The 50-product seed is unaffected: it still runs idempotently (`WHERE NOT EXISTS`) regardless of how many products have been added since.
- Currency is unspecified: prices render as plain `1,299.00` with no symbol.
- The success toast for a purchase is `NotificationService.show('Purchase recorded.')`, fired in `PurchaseService.purchaseProduct`'s `tap`.
- `.table-themed` has a 760px min-width; the product-details buyers table overrides it (`.buyers-table { min-width: 0 }`) because it lives in a half-width card and would otherwise scroll sideways and clip the date.
- Deep-linking a guarded route (e.g. pasting `/productDetails?id=…`) bounces to `/login?sessionExpired=true` — pre-existing SSR/auth behaviour (the server render has no `sessionStorage`), not specific to these pages. Test by logging in and navigating client-side.
- Purchases/products-listing were verified end-to-end against a real SQL Server (deployed the dacpac, ran the API, drove it with `curl`, and drove the UI in headless Chrome with axe-core: zero violations across those states). The stored procedures themselves have no unit tests — like the rest of the DB layer, they're covered by running the real stack. **Add-product is not yet verified this way** — `Product_Create` and the `/addProduct` UI were built and unit/type-checked (`ProductRegistrationTests.cs`, Angular specs, `tsc`) but not run against a live deployed DB; do that pass (`./build.sh && ./run.sh`, then add a product through the UI or `curl`) before treating this feature as fully confirmed.
