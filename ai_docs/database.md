# Database

## What it is

The `Customer`/`CustomerAddress`/`Merchant` schema, the status codes that drive the deactivate/reactivate/delete lifecycle, the stored-procedure layer, and the audit log.

- `API/.../CustomerManagementSystem.DataAccess/DBConnection/DbUtils.cs`, `DbHelper.cs`

## How it works

**`Customer`** (every column `NOT NULL` except `BirthDate`):
- `CustomerId` `UNIQUEIDENTIFIER`, **generated by the DB** (`DEFAULT NEWSEQUENTIALID()`) — see "GUIDs" below.
- `FirstName`/`LastName` `NVARCHAR(50)`.
- `Email` `NVARCHAR(254)` (the longest address SMTP can deliver to) and `PhoneNumber` `VARCHAR(15)` (the MSISDN: digits only; E.164's maximum), both unique. `NOT NULL` on both matters because SQL Server's `UNIQUE` treats every `NULL` as distinct, so a nullable column would let the uniqueness check be silently bypassed by a `NULL`.
- `Gender` `TINYINT DEFAULT 0` + `CK_Customer_Gender` (`0` = Not declared, `1` = Male, `2` = Female, see [angular-frontend](angular-frontend.md)).
- `BirthDate` `DATE NULL`.
- `StatusCode` `SMALLINT DEFAULT 1901` + `CK_Customer_StatusCode` (`IN (1901, 1903, 1904)`).
- `CreatedAt`/`LastInteractionAt` `DATETIME2(0)`, **UTC** (`DEFAULT SYSUTCDATETIME()`).

`IX_Customer_LastName_FirstName` (`LastName`, `FirstName`) backs the default unfiltered/sorted listing `Customer_List` does.

**Data-type conventions (all tables):** keys are `UNIQUEIDENTIFIER` (16 bytes; compared by value, so case and `{braces}` don't matter; can't hold a malformed value) — never the textual form in an `NVARCHAR`. Every timestamp is `DATETIME2(0)` written with `SYSUTCDATETIME()` (UTC), never `DATETIME`/`GETDATE()` (server-local) — the API marks what it reads as UTC and the UI converts to the viewer's zone. Codes are the smallest integer type that holds them, with a `CHECK` listing the valid values. Every proc parameter is declared with **the exact type of the column it's compared with**: in particular `@PhoneNumber` parameters are `VARCHAR(15)`, because comparing a `VARCHAR` column to an `NVARCHAR` value converts the column and turns `UQ_Customer_PhoneNumber` seeks into scans. Every constraint is explicitly named (see "Naming conventions" below) so a redeploy can re-check only the new constraint.

**`CustomerAddress`**: 1:1 with a customer via `CustomerId`, which is also the table's clustered **primary key** (`PK_CustomerAddress`) — that both enforces the 1:1 cardinality and gives the FK column an index (a FK alone doesn't index its referencing side). Previously the table was a heap with only a unique constraint. `ON UPDATE CASCADE` was dropped: a GUID primary key is never updated. country/county/town/zip/street/number, all `NOT NULL` (the API requires every one on registration). `Customer_Create` inserts both rows, and `Customer_Update` updates both, in **one transaction** each — `Customer_Get`/`Customer_List` `INNER JOIN` the two tables, so a customer row without a matching address row would silently disappear from every read despite existing in `Customer`.

**`Product` / `CustomerPurchase`**: a seeded 50-product catalogue and the customer↔product purchase link — schema, the seed, the `CustomerPurchase_Create` rules and the derived sold/inventory/left numbers are in [products-and-purchases](products-and-purchases.md). Two things matter from *this* doc's side: purchases are real FKs to `Customer`, so `Customer_Delete` deletes a customer's purchase rows first (inside its existing transaction, ahead of the address delete); and that delete does **not** restore product stock. A `Purchased` action now also appears in the audit log.

**`Merchant`**: `Username` (the API's "Merchant ID") is `NOT NULL` with `PRIMARY KEY (Username)`. Stores `PasswordHash`/`PasswordSalt` (see [api](api.md) for the hashing scheme) and `RoleCode`.

**`Customer_List` is paginated**, not a full-table dump: it takes `@PageNumber`, `@PageSize`, an optional `@SearchTerm` (`LIKE '%...%'` against first/last name, email, MSISDN — with `%`/`_` escaped via `@EscapedSearchTerm` + `ESCAPE '\'`, so a literal search for those characters doesn't match everything), and `@SortColumn`/`@SortDirection` (`name`/`email`/`msisdn`, `asc`/`desc`). Sorting is done via a parameterized `CASE`-based `ORDER BY` (no dynamic SQL — exactly one `CASE` pair is non-NULL per call) over `OFFSET`/`FETCH`, and each returned row carries a `TotalCount` column from `COUNT(*) OVER()` so the API can report `TotalItems` without a second query. `CustomerGetting.GetCustomersFunction` validates `PageNumber >= 1`, `1 <= PageSize <= 100`, and that `SortColumn`/`SortDirection` are in their allow-lists — `400` otherwise. The API wraps the page in `PagedResponse<CustomerModel>` (`Domain/Models/PagedResponse.cs`): `PageNumber`, `PageSize`, `TotalItems`, `Items`.

**Status codes** (`Customer.StatusCode`, the `CustomerStatus` enum in `Domain/Models/Enums.cs`):
- `1901` = active
- `1903` = deactivated
- `1904` = test — assigned only at creation time, by the About page's "add 50 test customers" bulk generator (see [angular-frontend](angular-frontend.md); it also gives each one 1–5 purchases — see [products-and-purchases](products-and-purchases.md)); marks a customer as fictitious/demo data everywhere the status is shown (UI status labels, CSV export). Unlike an active customer, a test customer is exempt from the deactivate-before-delete rule (see below) since it isn't real data.

**Lifecycle rules, enforced in the stored procedures themselves** (not just the API layer):
- New customers are created **active** by default (`Customer_Create`'s `@StatusCode` parameter defaults to `1901`); `CustomerRegistration.RegisterCustomerFunction` additionally accepts an explicit `1904` (test) in the request body, but rejects any other value with `400` — a client can never register a customer as already deactivated.
- `Customer_Deactivate` only updates rows where status `<> 1903` → `409` if already deactivated. A test customer (`1904`) can be deactivated the same as an active one; doing so moves it to the normal `1903` deactivated state, losing the test marker.
- `Customer_Reactivate` only updates rows where status `<> 1901` → `409` if already active. Reactivating a former test customer sets it to `1901` (active), not back to `1904` — the test marker doesn't survive a deactivate/reactivate round trip. This is a deliberate simplification, not a bug to fix.
- **`Customer_Delete` requires status `IN (1903, 1904)`** — deactivated or test. An active customer must be deactivated first; deleting one directly returns `409` with `'Customer must be deactivated before it can be deleted.'`. A test customer is the one exception to that guardrail and can be deleted straight from `1904`, since it's fictitious data with no lifecycle to protect. For a real (non-test) customer, only `deactivate → delete` or `deactivate → reactivate` are valid paths; `deactivate → delete → reactivate` is not (the customer no longer exists after delete).
- **Bulk delete** (customer-list page, see [angular-frontend](angular-frontend.md)): the UI lets any selection of customers be bulk-actioned. Active customers in the selection are only deactivated (not deleted, since they're not delete-eligible yet); deactivated/test customers in the selection are deleted outright. It's a client-side loop over the existing single-customer deactivate/delete endpoints (one HTTP call per customer, sequential), not a dedicated bulk endpoint or stored proc — so it's subject to the exact same per-customer rules as the single-row buttons, just batched with one confirmation prompt.
- `Customer_Create` also rejects duplicate `Email` or `PhoneNumber` up front with a friendly `400`, before attempting the insert. `UQ_Customer_Email`/`UQ_Customer_PhoneNumber` unique constraints on the table back this up as a DB-level safety net for the race window between that check and the insert (two concurrent registrations with the same email/MSISDN); a request that loses that race gets a `500` from the constraint violation instead of the friendlier `400`, via the proc's existing `TRY/CATCH`.
- `Customer_Update` uses `ISNULL(@param, column)` for every field, so **omitting a field in the edit request leaves it unchanged** rather than nulling it out — this is a partial-update endpoint, not a full replace. Like `Customer_Create`, it pre-checks email/msisdn for collisions with *another* customer (`400` if found, excluding the row being edited itself) and wraps both the `Customer` and `CustomerAddress` updates in one transaction with `TRY/CATCH` (`500` + rollback on failure) — the two tables can't be left out of sync by a partial failure. It also rejects any `CustomerStatus` other than Active/Test in the request (see [api](api.md) — edit is not a lifecycle-transition endpoint).

**CSV export** (`GET /api/Customer/export`): `CustomerGetting.GetCustomersForExportFunction` reuses the exact same `_dbUtils.GetCustomers` call (and therefore `Customer_List`) as the paginated `/all` endpoint — it validates/normalizes `SearchTerm`/`SortColumn`/`SortDirection` the same way, but fixes `PageNumber = 1` and `PageSize = MaxExportRows` (5000) internally instead of taking paging from the caller, so export honors the current search/sort but isn't limited to one page. The filtering/sorting SQL lives in exactly one place (`Customer_List`); no separate export stored proc exists. `CustomerCsvExporter.ToCsv` turns the resulting `List<CustomerModel>` into RFC 4180 CSV (with a leading UTF-8 BOM for Excel, and a leading `'` on any field starting with `=`/`+`/`-`/`@` to defang spreadsheet formula injection), and the controller returns it as a `text/csv` `File` result rather than the usual JSON envelope.

**Lookup**: `CustomerGetting.GetCustomerFunction` doesn't take an explicit search type from the caller — `DetermineLookup` tries (in order) `Guid.TryParse` → MSISDN format → email format and fills exactly one member of a `CustomerLookup`, which becomes exactly one of `Customer_Get`'s typed parameters (`@CustomerId UNIQUEIDENTIFIER`, `@PhoneNumber VARCHAR(15)`, `@Email NVARCHAR(254)`). An unrecognized `searchVariable` shape returns `404` without ever hitting the DB. `Customer_Get` is split into three standalone `IF @X IS NOT NULL` branches (one full `SELECT` each) rather than one query with a 3-way `OR`, so each search type gets a proper index seek instead of a scan.

**GUIDs are always generated by the DB**: `CustomerId`/`ProductId` default to `NEWSEQUENTIALID()`, so each new key sorts after the previous one and inserts append to the end of the clustered index instead of splitting random pages (a random `Guid.NewGuid()` key fragments it). `Customer_Create`/`Product_Create` capture the new key with `OUTPUT inserted.… INTO @Inserted` and return it as an extra `CustomerId`/`ProductId` column on the usual `(Result, Message)` row; the API returns it as the response's `Data`. The request models have no `Guid` member, so a client can never choose its own ID.

**Audit trail** (`CustomerAuditLog`): every successful mutation (`Created`/`Edited`/`Deactivated`/`Reactivated`/`Deleted`) writes a row via `CustomerAuditLogger.Log`, called from `CustomerRegistration`/`CustomerEditing`/`CustomerActivation`/`CustomerDeletion` only after the underlying DB call returns `Status == 200`. The merchant ID comes from `CustomerController.MerchantId` (`User.Identity.Name`, set from the JWT's `ClaimTypes.Name` claim — see [api](api.md)), not from the request body. **Deliberately no FK** from `CustomerAuditLog.CustomerId` to `Customer` — a deleted customer's audit history must survive `Customer_Delete`, which is the one place this table outlives the row it's about. Logging is **best-effort**: `CustomerAuditLogger.Log` swallows and logs (via `ILogger`) any exception rather than letting it bubble, because it always runs after the customer mutation it's recording has already succeeded — a logging failure must never turn that into a `500`. Read via `GET /api/Customer/auditLog?customerGuid=...` → `CustomerAuditLog_ListByCustomer`, newest first; `CustomerGetting.GetCustomerAuditLogFunction` validates the GUID format (`400` if not GUID-shaped) before hitting the DB.

**Global audit log** (`GET /api/Customer/auditLog/all`): a separate, paginated view across every customer, for the `/auditLog` admin page — not the same stored proc as the per-customer trail (that one returns every row for one GUID, unpaginated, which is fine at that scope; a global scan needs real paging). `CustomerAuditLog_List` follows `Customer_List`'s pagination convention (`@PageNumber`/`@PageSize`, `OFFSET`/`FETCH`, `COUNT(*) OVER()` for `TotalCount`) but has no search/sort — just newest-first. It `LEFT JOIN`s `Customer` to show a customer name; since the audit table has no FK (see above), a deleted customer's rows come back with `FirstName`/`LastName` `NULL` rather than disappearing, and `GlobalAuditLogEntry.CustomerFirstName`/`CustomerLastName` are mapped via `as string` (not `.ToString()`) specifically so that `NULL` surfaces as a real `null`, not `DBNull.Value.ToString()`'s empty string. A dedicated index, `IX_CustomerAuditLog_OccurredAt_CustomerAuditLogId`, backs this proc's unfiltered `ORDER BY OccurredAt DESC` scan — the existing `CustomerId` index only helps once a GUID is already known. `CustomerGetting.GetAllAuditLogFunction` validates paging the same way `GetCustomersFunction` does (reusing `MaxPageSize`). Per-customer audit log pagination was considered and deliberately skipped for now (small per-customer row counts don't currently justify it).

**Deletion**: `Customer_Delete` deletes purchases, then addresses, then the customer (all one transaction); it and `Customer_Create` access `Customer`/`CustomerAddress` in opposite orders (create: customer then address; delete: address then customer) — this is **not** reorderable. `CustomerAddress.CustomerId` has a `FOREIGN KEY` to `Customer` with no `ON DELETE CASCADE`, so referential integrity mandates address-row deletion before its parent customer row. The `PK_CustomerAddress` key (above) is the actual lock-footprint mitigation here, not reordering.

## Naming conventions

Applied on 2026-09-23 to all three sibling projects (customer-management-system, employee-management-system, imalo-education-webapp) so their schemas read the same way. Follow these for any new object:

- **PascalCase everywhere**: tables, columns, procs, parameters, result-set aliases, constraints. Acronyms are written as words (`Id`, `Json`, never `ID`).
- **No type or object-kind prefixes/suffixes**: no `tbl_`, no `usp_` (and never `sp_`, which SQL Server looks up in `master` first), no `_guid`.
- **Tables are singular nouns** (`Customer`, `Product`). A table owned by another starts with its owner's name: `CustomerAddress`, `CustomerPurchase`, `CustomerAuditLog`.
- **Keys**: the primary key is `<Table>Id` (`CustomerId`, `CustomerAuditLogId`); a foreign-key column has exactly the name of the key it references (`CustomerAddress.CustomerId`). A natural key keeps its natural name (`Merchant.Username`).
- **Column suffixes**: `…At` = a UTC moment (`DATETIME2`: `CreatedAt`, `LastInteractionAt`, `PurchasedAt`, `OccurredAt`); `…Date` = a calendar date (`DATE`: `BirthDate`); `…Code` = a coded value backed by a `CHECK` (`StatusCode`, `RoleCode`). Plain English over jargon/abbreviations (`PhoneNumber` not `msisdn`, `PostalCode` not `zip_code`), and no reserved words (`ActionType`, not `Action`).
- **Constraints and indexes are always named**: `PK_<Table>`, `FK_<Child>_<Parent>`, `UQ_<Table>_<Column>`, `CK_<Table>_<Column>`, `DF_<Table>_<Column>`, `IX_<Table>_<KeyColumn1>_<KeyColumn2>…`.
- **Procs are `<Entity>_<Verb>`**: `Create`, `Get` (one row), `List` (many rows / a page; `ListBy<Parent>` when filtered by a parent), `Update`, `Delete`, plus domain verbs (`Deactivate`, `Reactivate`, `GetAuthData`); a cross-entity aggregate is `Report_<Verb><What>`. Parameters are named exactly like the column they feed or compare with (`@CustomerId`, `@PhoneNumber`) — no `@var_` prefix. Local variables are PascalCase too (`@Result`, `@Now`).
- **Result-set columns are PascalCase** (`Result`, `Message`, `TotalCount`, `SoldQuantity`), and `DbHelper` reads them by exactly those names.
- **Files**: one object per file, named after the object (`Tables/CustomerAddress.sql`, `StoredProcedures/Customer_Get.sql`); seeds are `Scripts/PostDeployment/Seed_<Table>.sql`. The database (and `.sqlproj`) is `CustomerManagement`, no `_DB` suffix.
- **The API's JSON contract did not change with the DB names**: the JSON still says `guid`, `msisdn`, `zip`, `town`, `number`, `depot`, `comment`, `merchantId`, `action`, …; `DbHelper` is the one place the two vocabularies meet.

## Gotchas / conventions

- Every mutating stored proc's `(Result, Message)` convention is described in [api](api.md) — `Result = 0` success, nonzero maps directly to the HTTP status returned to the client.
- Every mutating proc that touches more than one table wraps its work in `BEGIN TRY/BEGIN TRANSACTION ... COMMIT TRANSACTION END TRY BEGIN CATCH ... ROLLBACK ... END CATCH` — match this pattern for any new multi-table proc.

## Known gaps / deliberately deferred

- A few procs return a raw `ERROR_MESSAGE()` string to the caller on unexpected `CATCH` failures. Left as-is — fixing this properly would need a server-side logging table to preserve debuggability once the raw message is no longer surfaced to the client, which is out of scope for this app's size.

**Resolved** (kept for history — don't rediscover these as "new" findings):
- **Naming pass (2026-09-23).** Every DB object was renamed to the "Naming conventions" above — was `tbl_customers`/`tbl_addresses`/…, `usp_getCustomer`/…, `PK_customer_guid`/`FK_customer_guid`, snake_case columns with stray capitals (`creation_Date`, `customer_Status`), `@var_`-prefixed parameters, auto-generated PK names, and the `Customer_Management_System_DB` database. The entries below use the new names. The renamed schema was deployed as a fresh database (the old one is left untouched on the container), not migrated in place.
- `Merchant` had no primary key/unique constraint, and `Username` was nullable — fixed: `Username` is now `NOT NULL` with `PRIMARY KEY (Username)`.
- `Customer.Email`/`PhoneNumber` uniqueness was enforced only in `Customer_Create`'s app-level `IF EXISTS` check, racy under concurrent registrations — fixed: `UQ_Customer_Email`/`UQ_Customer_PhoneNumber` unique constraints added as a DB-level backstop, and `Email`/`PhoneNumber` are now `NOT NULL` (closing the NULL-bypasses-uniqueness gap described above). The app-level check is still there for the friendly `400` message on the common case; the constraint closes the concurrent-registration race, degrading to a `500` (via `Customer_Create`'s existing `TRY/CATCH`) in the rare case both requests race past the check.
- `Customer_Update` had no transaction/duplicate-check and no `IF NOT EXISTS` 404 guard — fixed: see the `Customer_Update` bullet above.
- `Customer_Get` used one query with a 3-way `OR` across search types — fixed: split into per-search-type `IF` branches for proper index seeks, and `@var_SearchOption`/`@var_Gender` changed from `NVARCHAR` to `INT` end-to-end.
- `CustomerAddress.CustomerId` had no index/uniqueness — fixed: now the table's primary key (was `UQ_CustomerAddress_CustomerId`).
- **Data-types pass (2026-09-23).** GUIDs were `NVARCHAR(50)` (app-generated, compared as text — a `{braced}` GUID passed validation but never matched); `CreatedAt`/`LastInteractionAt`/`BirthDate` were `NVARCHAR(50)` (the first two held `GETDATE()`'s default string style, e.g. `"Sep 22 2026 5:47AM"`, so any date grouping needed `TRY_CONVERT`); every `DATETIME` was server-local `GETDATE()` read back without a zone, so the UI showed times off by the viewer's UTC offset; `Gender`/`StatusCode`/`RoleCode` were nullable `INT`s with no `CHECK`; `Email` was capped at 50; names, address fields and merchant password columns were nullable despite being required; `CustomerAddress` was a heap; `CustomerAuditLog.ActionType` was free `NVARCHAR(50)`. All fixed as described above. The SSDT publish migrates existing rows in place (implicit conversions, inside SSDT's own transaction) — verified against a restored copy of the dev DB with every row preserved.
